01何をするサービス？

国会では、毎年たくさんの議案（法律の案）が話し合われています。でも、議案の文章はとてもむずかしく、ニュースだけでは「結局なにが変わるの？」が分かりにくいことがあります。

みらい議会は、議案ごとにやさしい解説を用意し、分からないところをAI に質問できるようにしています。さらに、AI が聞き役になるインタビューで「この法律で自分の生活はどうなりそうか」を話すと、その意見がまとめられ、ほかの人の意見と一緒に公開されます。

このサービスは、じつは2つの Web アプリのセットです。

web/（だれでも見られる）

公開サイト

  • 議案の一覧と、会期（国会が開かれている期間）ごとのまとめ
  • 議案の解説（「説明をもっと詳しく」で切りかえ）とふりがな
  • チームみらいの賛成・反対と、その理由
  • AI チャットで質問
  • AI インタビューと、みんなの意見・トピックの一覧
  • 研究者などが使えるオープンデータ API
admin/（運営スタッフだけ）

管理画面

  • ログイン（メール・パスワード、または Google）
  • 議案の登録、解説の執筆、公開・非公開の切りかえ
  • 賛否と理由の登録（公開する日時の予約もできる）
  • インタビューの質問づくり（AI が手伝う）と試運転
  • 届いたレポートの確認と公開
  • 意見のトピック分析の実行
ポイント見る人用と管理する人用でアプリを分けておくと、公開サイトには「見せる・話す」機能しかないので、だれかが勝手に解説や賛否を書きかえる入り口ができにくくなります。

02全体の地図

ブラウザ（クライアント）はサーバーに HTTP のリクエストを送り、サーバーはデータベースや AI を呼び出して、結果をレスポンスとして返します。みらい議会には役割の違うサーバーがいくつかあります。

大事なのは、データベースが1つだけということです。管理画面で書いた解説を、公開サイトが読みだして表示します。そして、インタビューで話した内容も同じデータベースに保存され、管理画面から確認されます。

AI はどれも AI Gateway を通して呼び出します。使うモデルは "openai/gpt-5.2" や "anthropic/claude-haiku-4.5" のような文字列で指定するので、この文字列を変えるだけで OpenAI・Anthropic（Claude）・Google のモデルを切りかえられます。

03プログラムの役割分担

プログラムのファイルは千個以上あります。全部が好き勝手なことをすると、どこを直せばいいのか分からなくなります。そこでこのサービスでは、まず機能ごとに部屋（features/ フォルダ）を分け、さらに部屋の中を仕事の種類ごとのフォルダに分けています。画面を表示するときは、上のフォルダの関数が下のフォルダの関数を呼ぶ、という順番で処理が進みます。

URL を受けとるapp/…/page.tsx
URL（例：/bills/123）から「123番の議案のページだ」と読みとって、担当のフォルダに渡すだけ。
画面を組み立てるserver/components/
受けとったデータを並べて、画面の形にする。例：bill-detail-layout.tsx（議案ページ全体の並べ方）
データを用意する・操作を受けるserver/loaders/ ・ actions/
loaders は画面に出すデータを取ってくる。actions は「保存」ボタンなどの操作を受けとる。よく使うデータは作りおき（キャッシュ）しておく。
手順とルールを決めるserver/services/
「データを取る → AI に聞く → 結果を保存する」のような手順と、このサービスならではのルールを書く。例：handle-interview-chat-request.ts（インタビューの次の質問を決める手順）
データベースとやりとりするserver/repositories/
データベースの読み書きだけを担当する。ほかのフォルダはデータベースに直接さわらない。例：bill-repository.ts（議案を探す・数える）

ボタンを押したときの動きなど、ブラウザの中で動くコンポーネントは client/ に置きます。引数だけから戻り値が決まり、データベースや API にさわらない関数（純粋関数）は shared/ に置きます。純粋関数は同じ入力なら必ず同じ出力になるので、テストを書きやすくなります。

web/src/features/
├──bills/議案の一覧・詳細・検索・シェア
├──bill-difficulty/解説の「ふつう」「詳しく」の切りかえ
├──diet-sessions/国会の会期（第○回国会）ごとのまとめ
├──chat/AI チャットと、AI の利用料の管理
├──interview-config/インタビューの設定と質問
├──interview-session/インタビューの会話
├──interview-report/できあがったレポートと公開設定
├──report-reaction/レポートへの「参考になった」ボタン
├──user-topic-analysis/みんなの意見とトピックの表示
└──open-data/外部の人向けのデータ配布（API）

04議案ページが表示されるまで

スマホで /bills/123 を開いたときの処理のうち、URL を読んで HTML を返すという Web の基本の部分は省き、みらい議会ならではの処理だけを順に見ます。

作りおきを捨てるタイミング管理画面で解説や賛否を保存すると、管理画面のサーバーが公開サイトの /api/revalidate に POST リクエストを送り、"bills" というタグの付いたキャッシュをまとめて消します。次のアクセスでデータを取り直すので、直した内容がすぐに反映されます。

05AI に質問するしくみ

チャットの送信ボタンを押すと、ブラウザは会話の配列を JSON にして POST /api/chat に送ります。サーバーではこの順番で処理します。

06AI インタビューのしくみ

AI インタビューは、AI が質問して経験や考えを聞きとり、レポートにまとめる機能です。運営スタッフは管理画面で、議案ごとに質問の配列と、質問の進め方（モード）を決めておきます。

bulkまとめて聞くモード次の質問はサーバーが決める。まだ聞いていない質問のうち、配列の先頭のものを AI に指定する。
loopそのつど深ぼりモード次の質問は AI が決める。1つ答えるたびに、2〜3問の追加の質問で深ぼりする。
targeted相手を見て聞くモードloop と同じだが、質問ごとに対象者の条件を書ける。AI が会話から当てはまらないと判断したら、その質問を飛ばす。
試運転もAIで管理画面には、AI が回答者役を最大10人ぶん演じて、本番と同じ設定で模擬インタビューをする機能があります。インタビュアー役とは別の AI が満足度を採点するので、本番の前に質問の多さや聞き方を直せます。

07みんなの意見をまとめるしくみ

インタビューが何百件も集まると、全部読むのは大変です。そこで AI を使って、意見をトピック（話題）ごとに整理します。この重い作業は、公開サイトとは別の「まとめロボット」（Google Cloud の Cloud Run Job）が担当します。

まとめロボットの正体は、Google Cloud で動く1回きりのプログラム（Cloud Run Job）です。Cloud Scheduler が cron（0 6 * * *＝毎朝6時）で起動し、全部の議案をループで処理します。前回から新しい意見が増えていない議案は continue で飛ばすので、AI の利用料がむだにかかりません。管理画面のボタンからすぐに起動することもできます。

できあがったトピックは、公開サイトの「トピック一覧」に表示され、トピックをえらぶとそこに入っている意見が読めます。

08データベースの中身

データベース（PostgreSQL）は、行と列でできたテーブルの集まりです。テーブルどうしは外部キーでつながっています。たとえば bill_contents の各行は bill_id という列に、どの議案の解説かを ID で持っています。

かぎは全部サーバーにすべてのテーブルで RLS（行レベルセキュリティ）を有効にし、許可のルールは1つも書いていません。だからブラウザから直接は読めず、秘密の鍵を持つサーバーだけが読み書きします。サーバーは「このユーザーに見せてよいか」を if 文で確かめてから返します。

10ミスや悪用を防ぐしくみ

どれも「人が気をつける」だけに頼らず、プログラムで自動的に止めるようにしています。守っているものは、大きく分けてコード・AI・データの3つです。

コードのミスを、本番に入る前に止める

テスト（Vitest）

防ぐもの関数の計算や変換のまちがい

関数ごとに入力と期待する出力を書いて、自動で確かめる。データベースの関数は、手元で本物のデータベースを動かしてテストする。

型チェック（TypeScript）

防ぐもの「数値のはずが文字列だった」などのまちがい

変数や引数に型を書き、実行する前にまちがいを見つける。

書き方のチェック（Biome）

防ぐもの書き方のばらつきと、よくあるミス

コミットする前に自動で整形し、決めたルールに合わない書き方を知らせる。

自動チェック（GitHub Actions）

防ぐものチェックを通っていないコードが本番に入ること

プルリクエストのたびに、lint・型チェック・ビルド・テストを自動で実行する。

Codecov でテストの範囲を記録CodeRabbit が AI でコードレビュー

コミット前に整形プルリクエストで自動チェックテストと型がすべて通るマージして本番へ

AI の使いすぎと悪用を防ぐ

AI の利用料の上限

防ぐもの使いすぎや、いたずらで大量に質問されること

1人あたり1日、サービス全体で1日と1か月の上限を決め、こえたらリクエストを止める。

モデレーション

防ぐもの悪口や個人情報が入ったレポートの公開

別の AI がレポートを0〜100点で採点し、点数が高いものは自動では公開しない。

AI への入力の区切り

防ぐもの「今までの指示を忘れて…」と書いて AI をだます攻撃（プロンプトインジェクション）

利用者の文章は、毎回ランダムな文字列の区切りで囲んで、指示とは別のデータとして渡す。

データを守る

RLS（行レベルセキュリティ）

防ぐものブラウザからデータベースを直接読まれること

すべてのテーブルで RLS を有効にして、許可のルールを書かない。読み書きできるのは秘密の鍵を持つサーバーだけになる。

管理者のチェック

防ぐものスタッフ以外が管理画面に入ること

ログインしたユーザーに admin の役割があるかを、ページを開くたびに確かめる。

プレビュー用のトークン

防ぐもの公開前の議案を、URL を知っているだけで見られること

管理画面で有効期限つきのトークンを発行し、トークンが正しいときだけ公開前のページを見せる。

11用語集

議案
国会で話し合うために出された、法律などの案
会期
国会が開かれている期間。「第○回国会」と呼ぶ
リクエスト・レスポンス
ブラウザがサーバーに送るお願いと、その返事。URL・メソッド（GET や POST）・本文でできている
JSON
{ "name": "値" } の形でデータを書く書き方。API のやりとりや AI の出力に使う
API
プログラムからデータを取ったり送ったりするための URL の決まりごと
コンポーネント
画面の部品を返す関数。React では関数が JSX（HTML のような書き方）を返す
Server Component
サーバーで実行され、できあがった HTML だけをブラウザに送るコンポーネント
Client Component
ブラウザで実行され、クリックなどの操作に反応するコンポーネント。ファイルの先頭に "use client" と書く
Server Action
ブラウザから、サーバーの関数をそのまま呼べるしくみ。ファイルの先頭に "use server" と書く
async / await
時間のかかる処理（通信など）の結果を待つ書き方。Promise.all を使うと複数の処理を同時に待てる
外部キー
ほかのテーブルの行を ID で指す列。bill_contents.bill_id は bills の行を指す
純粋関数
引数だけで戻り値が決まり、外の世界（データベースや画面）を変えない関数
キャッシュ
一度計算した戻り値を保存しておき、同じ引数ならそれを返すしくみ
LLM
大量の文章で学習した AI のモデル。GPT・Claude・Gemini など
プロンプト
LLM に渡す指示の文字列。プログラムで組み立てて渡す
トークン
LLM が文章を読み書きするときの単位。利用料はトークン数で決まる
ストリーミング
レスポンスを一度に返さず、できた部分から順に送ること
モデレーション
不適切な内容がないかのチェック。ここでは AI が点数をつける
RLS
行レベルセキュリティ。テーブルの行ごとに、だれが読み書きできるかを決める PostgreSQL の機能
匿名ユーザー
名前やメールアドレスなしで作られる、ユーザーIDだけのアカウント
