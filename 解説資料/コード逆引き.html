01システム構成

Next.js のアプリが2つ（公開用 web と管理用 admin）で、データは Supabase に集まります。AI はすべて Vercel AI Gateway 経由です。重いトピック分析だけは Google Cloud の Cloud Run Job で動かします。

ロゴは Python の diagrams のアイコンを使っています。ローカルでは Supabase を npx supabase start で起動し、web は :3000、admin は :3001 で動きます。

04レイヤー構成

1つの feature の中は server / client / shared の3つに分かれ、server の中はさらに役割ごとのフォルダになっています。3つのまとまりに分けて見ていきます。

① サーバー側：上から順に呼び出す

画面を表示するときも、保存するときも、この順番で呼び出す。データベースにさわるのは一番下の repositories だけ。

app/…/page.tsx

URL のパラメータを受けとり、feature に渡すだけ

呼ぶ
server/components

Server Component。画面を組み立てる

データを頼む
server/loaders

読む。unstable_cache で作りおき

server/services

手順とルール。AI 呼び出し・副作用

server/repositories

Supabase の読み書きだけ（find* / create* / update*）

簡単な読み取りでは services を通らず、loaders から repositories を直接呼ぶこともある。

② 操作と API：書きこみの入口は2つ

画面の操作は Server Action、チャットのような長い処理や外部向けは route.ts（API）から入る。

client/components

"use client"。ボタンや入力欄

Server Action を呼ぶ
server/actions

"use server"。入力チェックして保存

repositories

保存する

client/hooks

fetch で /api を呼ぶ。ストリームを受けとる

fetch
app/api/…/route.ts

認証と入力チェック

server/services

AI を呼ぶなどの処理

③ 共通の部品とルール

どこからでも使えるものと、置き場所のルール。

shared/types・utils

純粋関数。サーバーでもブラウザでも動く。*.test.ts を同じ場所に置く

packages/

web と admin の両方で使うロジック。同じコードを2か所に置かない

"server-only"

サーバー側のファイルの先頭に書き、ブラウザに混ざるのを防ぐ

詳しいルールは docs/repository-layer.md と AGENTS.md にあります。

06データモデル

テーブルは supabase/migrations/ の SQL（108ファイル）で作られます。中心は bills で、インタビューとトピック分析がそこにぶら下がります。

PK主キーFK外部キー（ほかの表の行を指す）IDID を持つだけ（制約なし）ほかのまとまりのテーブル線の先が分かれている側が「多」（1対多）

① 議案まわり

中心は bills。解説・賛否・タグ・プレビューの合言葉が、議案1件にぶら下がる。

② インタビュー

設定 → セッション（1人1回）→ 発言とレポート → 意見1件ずつ、の順に細かくなる。

③ トピック分析

分析を実行するたびに version を作り、その中にトピックと「意見の割り当て」を保存する。

④ 利用者と記録

ユーザーは Supabase の auth.users。利用額や回数制限の記録もここ。

すべてのテーブルで RLS を有効にし、ポリシーは作りません。ブラウザから直接は読めず、サーバーが秘密鍵で読み書きします。列は主なものだけです。
